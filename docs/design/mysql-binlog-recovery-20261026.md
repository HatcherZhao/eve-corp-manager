# MySQL 日志膨胀故障处理

日期：2026-10-26，北京时间。运行应用仍为 `c5ed473`，未重新部署应用或轮换机器人密钥。

## 故障与根因

- 网站首页和 MCP 认证正常，机器人既有密钥可成功列出四个工具。
- 业务查询耗时约 52 秒后返回 `访问记录暂时不可用`。审计写入失败时系统按既有安全规则不返回数据，不能将其解释为空数据。
- 共享数据库服务器根盘 191 GB 已用满；MySQL 有 261 个在线 binlog，合计约 162 GiB。
- 原配置已经启用 7 天自动过期，并非无限保留；原 `binlog_row_image=FULL` 放大了更新量。
- 市场快照表有 20,034 行，历史 JSON 约 312.2 MiB，买卖订单 JSON 合计约 17.8 MiB。历史和订单存在同一行，订单更新会使 FULL 模式同时记录未修改历史的前后镜像。
- 抽查两个完整日志，市场快照事件分别约 678.5 MiB、664.0 MiB，占对应文件超过 99%；每天产生约 25 GiB 日志。该数字是数据库日志量，不是官方接口下载量。
- `max_binlog_size=100M` 不是大事务的硬上限，MySQL 不会为满足该值而拆开完整事务。

## 已执行操作

1. 核对注册副本、本机复制状态、复制配置和 Binlog Dump 连接，未发现现有复制依赖。
2. 删除一份约 662 MiB、可重新下载的系统 RPM 缓存，仅用于腾出应急操作空间；没有删除业务文件。
3. 数据库完成之前受阻的提交后，使用机器人原密钥查询月矿恢复成功，实测约 1.85 秒。
4. 备份现有 MySQL 配置，通过 `SET PERSIST binlog_row_image='NOBLOB'` 避免无关大文本重复入日志。实际修改的大文本仍然记录，没有关闭 binlog。
5. 最初将少量旧日志逐份压缩、完整读回并校验 SHA-256，写入持久化清单后通过 `PURGE BINARY LOGS TO` 清理在线副本。归档共约 675 MiB，仅为本次应急留存。
6. 用户随后明确缩短日志保留期，停止继续归档，通过 `SET PERSIST binlog_expire_logs_seconds=172800` 设置两天自动保留，再通过 MySQL 正规清理两天以前日志。
7. 日志清理不会删除当前业务记录，但两天以前未归档的日志不再可用于按时间点回放。没有执行 RESET MASTER、直接删除数据库文件、清 Redis 或重启共享数据库。

检查时磁盘降至约 37%，可用约 122 GB；中间曾为 44%、可用约 108 GB，随后数据库继续回收阻塞事务相关空间。

- 新建连接已采用 NOBLOB；既有连接保留旧会话值，随连接池正常轮换生效，没有为了立即切换而强制断开业务连接。

## 市场同步方式

- 后台抓取一个区域的完整订单分页，再筛选吉他星系；默认不限定单一空间站。
- 当前不是增量订阅。从生产 Redis 已缓存的官方响应元数据核实，当前 `X-Pages=132`；没有为测量页数额外请求官方。
- 全部页面成功后，事务发布一轮快照；每种物品仅保留买卖各最多 100 条展示订单，报价和挂单量仍从完整筛选结果计算。
- 单轮结束后至少等待 15 分钟，同时尊重官方 Expires；每分钟调度只检查共享门禁，不等于每分钟抓取市场。
- 全站官方 ESI 请求共用至少 3 秒的启动间隔，市场分页顺序读取，多实例共用锁；缓存有效时不请求，过期时发送 ETag 条件校验，收到 304 复用正文。
- 市场历史每 5 分钟最多补齐 1 个物品，单物品成功后至少间隔 1 天，或更长的官方缓存期。
- 420、429、Retry-After 和错误额度反馈会触发共享冷却。不能据此承诺绝不会被封禁；当前没有完整的上游请求数量、字节和 304 命中率监控。
