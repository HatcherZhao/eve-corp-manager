# 月矿堡矿种与产出比例档案

## 业务口径

- 以租户、军团绑定、建筑 ID 唯一保存长期档案，同一矿堡的不同提取轮次共用。
- 保存矿种及产出比例，不保存每轮绝对体积、产量或排产周期。
- 比例来自同一封游戏通知的 `oreVolumeByType`：单矿种体积除以该通知全部矿种体积。服务端保存 0 到 1 的十位小数，页面显示百分比。
- 所有正体积矿种均参与计算；名称无法识别时保留物品类型占位，不丢弃其比例。任一体积无效时拒绝整封通知，避免生成失真的比例。

## 数据与初始化

新增 Liquibase 迁移 `053_moon_ore_profile.sql`，建立 `eve_moon_ore_profile`，状态为 `PENDING`（等待通知）或 `READY`（已有档案）。

月矿列表查询及时间线同步时，幂等创建缺失档案，只检查本人当前角色的本地通知缓存。普通列表不访问 ESI；没有通知授权的成员仍能查看军团共享档案。已 READY 的档案不再自动读取通知或覆盖。

PENDING 的普通本地检查间隔十分钟；通知正常同步成功后立即尝试补全，不受此间隔影响。没有可用通知时保留占位，等待后续通知或手动刷新，不推测矿种。

采用包含有效矿种的最新通知，支持 `MoonminingExtractionStarted`、`MoonminingExtractionFinished`、`MoonminingAutomaticFracture`、`MoonminingLaserFired`。有建筑 ID 时同时匹配月球和建筑；缺少建筑 ID 时，只有军团完整 ACTIVE 时间线中该月球唯一对应一个矿堡才允许匹配。

## 手动刷新与页面

`POST /eve/extractions/{extractionId}/ore-profile/refresh` 需要 `eve:extractions:manage` 权限。先验证当前军团的 ACTIVE 时间线，再同步本人通知并重算目标档案。未找到有效消息、接口失败或消息比已有来源更旧时，不清空或降级已有档案。

列表展示矿种和比例，详情展示全部矿种、来源通知时间和档案更新时间。搜索条件支持矿种名称，并与精炼厂、月球、星系等条件共用分页。一次刷新会同步更新页面中同堡的所有时间线与已打开的详情。

## 隔离与上游保护

- 私人通知严格按 `tenant_id + user_id + character_ref_id` 读取，并验证当前角色、军团、服务器和有效通知 Scope。
- 军团共享响应仅包含矿种、比例、状态和时间，不返回通知正文、通知 ID 或操作人。
- 通知的自动和手动同步共用角色级 Redis 锁、上游缓存有效期和失败退避；空结果同样缓存，成功门禁在本地事务提交后发布。
- ESI 客户端现有全局限速与 Retry-After 处理继续生效，不引入新的通知轮询任务。
